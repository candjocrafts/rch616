Apache Kafka

A concise, bank-relevant explainer for understanding event streaming, practical applications, and the questions worth asking.

1.In plain English

Apache Kafka is software for publishing, storing, and reading streams of records (“events”) across distributed systems. Producers write events to named topics; consumers read them independently, and Kafka retains records according to configured policies, enabling later replay. It is not a system of record, an enterprise data warehouse, or by itself a business workflow/control solution. Ordering is guaranteed only within a partition, not across an entire topic. Apache Kafka Introduction · Apache Kafka Design

2.Problems it can help solve

  • Slow, point-to-point integration: Kafka can distribute the same event stream to multiple independent consumers rather than requiring every producer to build a direct interface to every downstream system. Dependency/limitation: topic design, schemas, ownership, and consumer error handling must be governed. Source
  • Need to react to events quickly: Consumers can process events as they are produced; Kafka Streams supports applications that transform, aggregate, and join streams. Dependency/limitation: end-to-end latency also depends on source systems, network, consumer capacity, and failure handling. Kafka Streams
  • Reconstructing downstream state: Configured retention and consumer offsets allow consumers to reread data from a chosen point. Dependency/limitation: retention, access, sensitive-data handling, and replay procedures require explicit control design. Source

4.Glossary

Event
A record that something happened, such as a payment status changing.
Topic
A named stream to which events are written and from which they are read.
Partition
A topic subdivision that enables distribution and defines the scope of record ordering.
Consumer group
Consumers cooperating so each partition is assigned to one group member at a time.
Offset
A consumer’s position in a partition, used to resume or replay processing.

5.In a large global bank

Illustrative application—not a client-specific design: A payments operations owner could use Kafka to distribute payment-status events from a payment-processing domain to fraud operations, customer-notification, liquidity-monitoring, and analytics services. Each consuming team would have a separate consumer group and could operate at its own pace; source-system identifiers, timestamps, status codes, and carefully classified customer/account references might be included.

An integration team would define event contracts and schemas; domain owners would own event quality; platform operations would monitor capacity, replication, access, and recovery; and control owners would approve data classification and retention. Potential success indicators include time from status change to downstream availability, consumer lag, failed-processing rate, and completeness/reconciliation exceptions. This is an inference, not a proven bank outcome; validate architecture, data, process, and control requirements with the bank.

Bank control considerations: Establish least-privilege authentication/authorization, encrypted transport where required, auditability, data classification and retention rules, resilience/failover testing, and third-party/dependency responsibilities. Kafka documentation describes SSL/TLS, SASL authentication, authorization, quotas, and audit-log capabilities, but these are platform features—not proof that a given deployment meets bank requirements. Apache Kafka Security Basel’s operational-resilience principles provide a useful cross-border reference point for identifying and managing operational-resilience risk; this is not legal or compliance advice. 6.Discovery questions / watch-outs

  • Which business events need distribution, who owns each event contract, and which consumers are critical? Unclear ownership can create unreliable downstream use.
  • What recovery point, recovery time, replay, and reconciliation requirements apply? Retention and replication settings alone do not define business recovery.
  • Which data classifications may enter events, and how will access, masking/minimization, retention, and audit evidence be handled?
  • Validate with architecture, security, privacy, resilience, and relevant risk/control owners as applicable.
